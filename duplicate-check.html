Questions for Sagar

  • ?What identifier does it key on — phone only, or email too? Are both normalized, and how?
  • ?Plaintext or hashed? If hashed, which algorithm, and is it salted or keyed? A bare SHA-256 of a phone number is brute-forceable — the keyspace is small enough to rainbow-table in hours, so an unkeyed digest is not real protection.
  • ?Global or per-affiliate? A shared global file tells every affiliate what every other affiliate has sold. A per-affiliate HMAC key fixes that and makes a leak attributable.
  • ?Do entries expire at 365 days? If the file only ever grows it over-suppresses, and affiliates quietly lose volume they were entitled to send.
  • ?How is it delivered and how often — SFTP drop, signed URL, API? Full file or deltas? Full is self-healing; a missed delta drifts silently.
  • ?Is the file built from the same source as the duplicate rejection rule? This is the one that matters most — see below.
  • ?Who can reach it today, and is that access authenticated, logged and rate-limited?

Proposal — close the loop on duplicate rejections

When we reject a lead as a duplicate, that number should end up in the suppression file. But it is worth being precise about why, because in the healthy case it is already there. A duplicate rejection means the number is inside the exclusivity window by definition — so if the file were complete, current, and correctly matched, that lead should never have been sent. Every duplicate rejection is therefore evidence of one of four things:

  • 1The affiliate is not using the file at all.
  • 2They are matching against a stale copy.
  • 3Normalization mismatch — leading 1s, extensions, formatting. Their number and ours hash differently, so a real entry silently fails to match. This is the most common cause and the least visible.
  • 4The file does not cover everything the rejection rule covers. Only this one is actually fixed by adding the number — the other three are integration faults.

So the ask is: write it to the file, and record which of the four it was. The write is cheap insurance; the classification is the valuable part, because it turns every duplicate rejection into a free integrity test of the file. If an affiliate adopts the file and their duplicate rate does not fall, something is broken — and today we would have no way to tell which thing.

Worth measuring either way: duplicate rejection rate before and after an affiliate starts consuming the file. That single number tells us whether the file is doing its job, and it is currently the largest rejection reason on the Heritage account.
